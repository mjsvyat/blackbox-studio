# CLAUDE.md — как работать с Blackbox Studio

Пользователь летает и паяет, но не теоретик управления. Каждая цифра в UI должна
иметь подсказку «что это / почему плохо / что крутить / чем платим». Язык — русский,
общаться с пользователем тоже по-русски.

Исходное ТЗ — `docs/PROMPT.md` (8 этапов). Статус этапов, архитектура и ограничения —
`PLAN.md`. Начинать каждую сессию с этих двух файлов и этого.

## Перед любой правкой

1. `npm test` — всё зелёное (большой дамп ~20 с). Тесты читают настоящие логи из
   `tests/fixtures/`: `blackbox-2026-09-06.txt` (3 МБ, 5 логов, BF 2026.6.1, 2 кГц) и
   `blackbox.txt` (132 МБ, Git LFS, BF 4.5.2, 1 кГц, заворот флешки на 64 МиБ).
   Без `git lfs pull` тесты большого дампа пропускаются (не падают) — для полной
   проверки сначала `git lfs pull`.
2. `npx tsc --noEmit`.
3. `tests/fixtures/legacy/bbdec.cjs` — копия рабочего декодера пользователя (оригинал
   у него в `Desktop\claud\bb-tools`), эталон для тестов. Не редактировать.
4. Логи пользователя — личные данные (GPS, ID платы): репозиторий приватный, логи
   никуда наружу не отправлять.

## Инварианты (не ломать)

- **Декодер = bbdec.js кадр в кадр** (`tests/decoder.test.ts`, `tests/big-dump.test.ts`).
  Единственные сознательные отличия: predictor INC учитывает P interval; TAG2_3SVAR как
  в blackbox-tools; LOGGING_RESUME сбрасывает историю; float в INFLIGHT_ADJUSTMENT — 4 байта.
  Новое отличие — только с тестом и записью сюда.
- Эталонный npm-парсер `blackbox-log` (0.2.2) на логах 4.5+ **ошибается** (история
  AVERAGE_2 после I-кадра). Не «чинить» наш декодер под него.
- Частота логирования — всегда из заголовка (`looptime`, `pid_process_denom`,
  `P interval`); по меткам времени — только предупреждение (на битом логе медиана врёт).
- Дамп не читать целиком: только `ByteReader` кусками.
- Пороги — только в `src/config/analysis.json`, тексты — только в `src/content` и
  `src/i18n/ru.ts`. В коде порогов и русских фраз нет (кроме комментариев).
- Удары/срывы исключаются из спектров (`rejectBursts`), иначе один кувырок «перекрашивает»
  весь полёт.
- Прогноз никогда не выдаётся за факт (с этапа 7): пунктир + полоса + подпись.
- Рейты = `rc.c` один в один (`tests/rates.test.ts`): самопроверка на всех логах — 100 %
  совпадения с записанным setpoint на стоячем стике. Если на новом логе не 100 % — сначала
  искать переключение rate profile / режимы, а не «подкручивать» формулы.
- Step response — МНК с выбором строк + отбеливание (`pid/stepResponse.ts`); синтетика в
  `tests/pid.test.ts` (±4 п.п.) — эталон. Спектральный метод по окнам на настоящих логах
  занижал ответ — не возвращаться к нему без сравнения на синтетике И логах.
- Порт simplified_tuning.c сверен с заголовками логов 4.5.2 и 2026.6.1 до единицы; версии
  различаются (D_MIN ≤ 4.5, D_MAX ≥ 2025.12). `set simplified_*` PID не пересчитывает —
  советы всегда выдают готовые `p_/i_/d_/f_`.
- Советчик: правило = ID + version; изменил логику — подними version и запиши в `_history`
  раздела `advisor`. Механика блокирует настройки; ≤ 2 изменений и ≤ 1 «рискованного» за
  итерацию (`tests/advisor.test.ts`).
- Весь путь «лог → анализ → советы → снимок» — `analysis/pipeline.ts`; воркер и тесты зовут
  его же. Новые расчёты добавлять туда, а не в воркер, иначе тесты проверяют не то.
- Сессия хранит снимок (`sessions/snapshot.ts`, `SNAPSHOT_VERSION`), не лог. Поменял формат —
  подними версию и сохрани чтение старых (у пользователя в IndexedDB старые снимки).
- Прогноз в сравнении — только если план применён (по заголовку «стало»).
- Модель оси (`sysid/`): объект подбирается по измеренному step response, не «по времени»
  (на логах это даёт fit ≈ 0 — см. PLAN.md, этап 7). Эталон — синтетика в
  `tests/sysid.test.ts`: прогноз ±4 п.п. / ±3 мс от истинного отклика. Правка модели, ломающая
  это, неверна. Прогноз всегда с полосой и подписью «модель, проверь полётом».
- CLI — только через `cliDiff` (`params/registry.ts`): перечисления пишутся словом
  (`set rates_type = ACTUAL`), числа BF CLI для них не принимает.
- Подсказка, которая поднимает D или ослабляет фильтры, обязана содержать: «короткий
  висящий полёт 20–30 с и потрогать моторы; горячие — откат».

## Модель фильтров (этап 2) — инварианты

- Порядок звеньев и формулы — в шапке `src/filters/chain.ts`; менять только со ссылкой
  на исходник Betaflight нужной версии и с прогоном `tests/filters.test.ts`.
- Эталон точности: лог 2026.6.1 №4 (2 кГц) — совпадение ≥ 90 % по всем осям, D-корр > 0.9.
  Если правка это ломает — правка неверна.
- Падение точности на 1 кГц — следствие алиасинга (доказано прореживанием 2 кГц-лога),
  не «чинить» модель под 4.5.2-логи.
- Метрика совпадения вычитает дисперсию округления лога (1/12); спектральное сравнение
  добавляет к модели белый пол округления. Без этого чистая модель выглядит «неточной».
- Задержка — фазовая, в операционной точке (медианы газа/оборотов/центров дин. нотча).
- Simplified: множитель меняет только ненулевые фильтры (как simplified_tuning.c).
  Ручные значения, расходящиеся с множителем, → в CLI добавляется simplified_*_filter = OFF.

## Изменение порога

1. Поменять значение в `analysis.json`.
2. Добавить запись в `_history` соответствующего раздела: `{ "version": "1.1", "was": …,
   "now": …, "why": "…", "by": "INC-xxxx или наблюдение" }`, поднять `version`.
3. Обновить числа в подсказках `src/content/help/*.md`, если они там упомянуты.
4. `npm test`.

## Разбор инцидента

Пользователь пишет инцидент в утилите (вкладка «Сессии» → ⚠) и скачивает zip папки случая.
Папка `cases/INC-xxxx-<симптом>/`:
- `case.md` — для чтения: симптом, что советовали (ID+версия правил, входные цифры), что
  реально применено (по заголовку лога), метрики было/прогноз/стало, признаки, подозреваемые;
- `case.json` — всё машинно (`incident`, `before`/`after` — полные снимки сессий, `auto`,
  `rollback`, `regression` — заготовка проверок);
- `before.bbl` / `after.bbl` — байты логов (если файл был открыт) или `logs.md` со смещениями;
- `plots/*.png`, `resolution.md` — шаблон разбора.

Порядок:
1. Воспроизвести: `case.json → regression.log` (`{ "file": "before.bbl" }` или
   `{ "fixture": "…", "logIndex": N }`) — `tests/cases/cases.test.ts` прогоняет его полным
   конвейером (`analysis/pipeline.ts`).
2. Отделить ошибку утилиты от механики/внешних условий (ветер, другой пакет, сбитый проп —
   смотри `auto.comparability`, разброс моторов, спектр до фильтров, `auto.findings`
   «mechanics», вкладку событий). Если план не применён (`auto.plan.state`) — советы ни при чём.
3. Найти правило/порог/модель. Лестница правки: уточнить условие → сдвинуть порог → уменьшить
   шаг → добавить предупреждение → отключить правило для класса бортов
   (`advisor.disabledRules` или профиль борта).
4. Регрессия: заполнить `regression.checks` (`not-selected`, `not-fired`, `fired`, `selected`,
   `first`, `metric {path, min, max}`); по возможности `regression.oldBehavior` — пороги до
   правки, на которых проверка обязана падать.
5. Прогнать все случаи (`npm test`); правка, ломающая старый случай, не принимается.
6. Поднять `version` правила (если менялась логика) и конфига, запись в `_history` с
   `"by": "INC-xxxx"`, заполнить `resolution.md`.

Пример полного цикла: `cases/INC-0001-hot-motors/` (демо: симптом выдуман, правка настоящая).
Автоматика без Claude: правило, ухудшившее результат на борту в ≥ 2/3 применений (≥ 2 раз),
само становится «с осторожностью» (`incidents/incidents.ts → ruleStats/boardKnowledge`).

## Полезное

- Проверка в браузере: `npm run dev` (порт 5181), загрузить дамп в `input[type=file]`:
  Playwright — `page.setInputFiles('input[type=file]', 'tests/fixtures/…')`; или в
  странице `fetch('/tests/fixtures/blackbox-2026-09-06.txt')` → `File` → `DataTransfer`
  → `input.files` + событие `change`. Лог №4 малого дампа — основной для проверок.
- Сборка воркера только `iife` (vite.config.ts): module-воркер из blob не стартует на
  `file://`, а `dist/index.html` должен открываться двойным кликом. Проверять сборку
  через `file://` после изменений воркера.
- Bash-heredoc с обратными кавычками и кириллицей в Git Bash на Windows ломается —
  большие правки делать через Edit/Write или скрипт-файл.

## Борт пользователя и что уже известно

- TMOTOR Velox F7 SE (STM32F722, ICM42688P, шкала ±2000 °/с), 6S, CRSF, DShot600
  bidirectional, 14 полюсов, BF 2026.6.1. Флешка W25N01GV: в ≤ 2026.6.1 заворот адреса
  на 64 МиБ (PR #15524) и дубль 64-байтного куска в строке заголовка (PR #15525) —
  оба обрабатываются декодером.
- Настройки из CLI-бэкапа (в логах 4.5.2): gyro LPF1 выкл., LPF2 800, dyn notch 2× Q4
  90–800, RPM Q10, D-term 105/210, simplified gyro ×160, D ×140. Логи 2026-09-06 — на
  дефолтах 2026.6.1 (LPF1 дин. 250–500, RPM Q5).
- 2026-09-06 №4: два срыва (~21.8 и ~26.1 с) — моторы 0↔100 %, gyroUnfilt до 11.5 мс
  в упоре ±2000 по трём осям, PID обнулён. Вне срывов борт тихий. №3 — ~97 % битых данных.
- Датчик тока во всех логах упирается в «полку» 124–164 А.
- На дефолтах 2026.6.1 RPM-нотчи (Q 5.00) — ~60 % задержки гиро-цепочки на 100 Гц.

## Идеи, обсуждённые с пользователем (не в исходном ТЗ)

- «Автотюн» = полуавтоматический цикл ТЗ (советчик → песочница → полёт → сравнение),
  в полётник утилита ничего не пишет. Мастер итераций частично сделан на этапе 4: правило
  R-STEP-DATA-01 и подсказка test-flight говорят, какой полёт сделать, если манёвров мало и идентификация по CHIRP-полёту (этап 7;
  проверить по исходникам, есть ли режим CHIRP в 2026.6.1). Решение пользователя — ждёт.
