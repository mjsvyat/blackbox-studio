## A. Обкатка: «кампания настройки» и калибровка по реальным полётам

Утилита уже умеет: сессии, сравнение «было / прогноз / стало», инциденты, калибровку
полосы прогноза. Не хватает **процесса**, который ведёт пилота через 5–10 итераций и
превращает их в проверенные пороги.

1. **Кампания** — серия сессий одного борта с общей целью («убрать пропвош», «холоднее
   моторы»). Экран кампании: лента итераций (что предложено → что применено (по
   заголовку следующего лога) → что вышло), график ключевых метрик по итерациям
   (шум после фильтров, D-term RMS, overshoot, задержка фильтров, температура моторов
   из отметок пилота).
2. **Протокол тестового полёта** для каждой итерации: что слетать (висение 20 с,
   флипы по ролл/питч, панчи, сбросы газа, тот же пакет и похожий заряд), чек-лист
   перед вылетом (стереть флешку, 2 кГц, gyroUnfilt в логе, тот же пропеллер). После
   загрузки лога — автоматическая проверка: хватает ли каждого вида манёвров, сопоставим
   ли полёт с прошлым (бины газа, интенсивность стиков, напряжение). Если нет — честно
   сказать, что сравнение некорректно и что дослетать.
3. **Точность прогнозов по истории**: таблица по каждой метрике и каждому правилу —
   сколько раз прогноз попал в полосу, средняя ошибка, «стало лучше / хуже». Это уже
   частично есть (калибровка) — сделай видимым и понятным.
4. **Предложения по порогам** (не автоприменение!): если за кампанию накопились
   данные, что порог явно не там (например, «зелёный» D-term на этом борту всё равно
   греет моторы), утилита формирует **отчёт-предложение**: какой порог, было → предлагаю,
   на каких сессиях это видно, какие прошлые случаи это затронет. Применяет человек
   (через правку `analysis.json` с записью в `_history`) или Claude в новой сессии по
   инструкции из `CLAUDE.md`.
5. **Экспорт кампании** одним файлом (JSON + HTML-отчёт), чтобы её можно было приложить
   к разбору в новой сессии Claude.

Проверка: тест на синтетической кампании из 6 сессий (два правила, одно стабильно
помогает, другое дважды ухудшило) → правило «с осторожностью», отчёт-предложение
порога с правильными ссылками на сессии; проверка сопоставимости полётов на парах
«висение vs фристайл» (должна ругаться) и «два похожих полёта» (не должна).

## B. Подключение к полётнику по USB (Web Serial + MSP)

Цель: убрать ручной цикл «конфигуратор → скачать → открыть → скопировать CLI».

**Возможности по порядку важности:**

1. **Подключение и чтение**: Web Serial (Chrome/Edge), выбор порта, MSP v1/v2.
   Показать: плата, прошивка и версия, имя крафта, состояние (armed / disarmed),
   статус флешки (размер, занято, готовность).
2. **Стереть флешку** одной кнопкой (с подтверждением и ожиданием окончания стирания,
   прогресс). Для W25N01GV на ≤ 2026.6.1 — это главный способ не получить заворот
   адреса; напоминание «стёрто ли перед полётом» — в протокол тестового полёта (A2).
3. **Скачать блэкбокс** с флешки прямо в утилиту (чтение кусками с прогрессом, повтор
   при ошибке CRC, возможность прервать), сразу открыть как файл. Сохранить копию на
   диск — по кнопке (File System Access API или скачивание).
4. **Прочитать текущие настройки** борта (`diff all` через CLI-режим или MSP) и
   использовать их как «сейчас на борту» вместо заголовка последнего лога; показать
   расхождения «заголовок лога ↔ борт» (например, «после полёта уже меняли D»).
5. **Применить CLI-блок** из советчика или песочницы — **только** по явной кнопке,
   только на disarmed-борту, с показом diff перед отправкой, автоматическим бэкапом
   `diff all` «до» (сохраняется в сессию), построчной проверкой ответа CLI (ошибки
   «Invalid name / value» — остановиться и показать), `save` в конце. Кнопка «Откатить»
   — применить бэкап.

**Обязательно:**
- Перед реализацией **сверить по исходникам Betaflight 2026.6** (msp_protocol.h, msp.c,
  cli.c): коды команд для сводки/чтения/стирания флешки (в 4.x это
  `MSP_DATAFLASH_SUMMARY` / `MSP_DATAFLASH_READ` / `MSP_DATAFLASH_ERASE`), формат ответа
  чтения (возможное сжатие Huffman), вход в CLI и выход без перезагрузки. Не писать по
  памяти — записать найденное со ссылками в `PLAN.md`.
- Протокол — отдельный модуль (`src/fc/`) с тестами на записанных байтах: эмулятор
  полётника (фейковый порт), который отвечает как Betaflight, включая ошибки CRC,
  обрыв, медленное стирание.
- **Безопасность**: никогда не посылать команды, которые могут крутить моторы
  (`MSP_SET_MOTOR`, моторный режим и т. п.); любые записи — только если борт disarmed
  (проверять перед каждой записью); никаких записей без нажатия пользователя; пропы
  снять — напоминание при первом подключении.
- Web Serial требует безопасного контекста: проверь, работает ли он на `file://`; если
  нет — честно показать в UI «подключение к полётнику работает только через
  `npm run dev` (localhost)» и не ломать остальное.
- Совместимость: если версия прошивки/MSP не поддерживается — сказать какая нужна,
  ничего не писать.

Проверка: тесты протокола на эмуляторе; ручная проверка на борту по чек-листу в
`PLAN.md` (подключить → прочитать → стереть → слетать → скачать → открыть →
применить совет → откатить), с пропами снятыми.

## C. Идентификация по chirp-полёту («почти автотюн»)

В Betaflight 2025.12+ появился режим **CHIRP** (декодер уже знает этот бит, анализ PID
сейчас его участки выкидывает). Полётник сам подаёт на выбранную ось синусоиду с
нарастающей частотой — идеальное возбуждение для идентификации.

1. **Сверить по исходникам** 2026.6: как включается (режим на тумблер), параметры
   (амплитуда, частоты, длительность, ось — имена в CLI), что пишется в лог (setpoint?
   отдельное поле? debug_mode?). Записать в `PLAN.md`. Если в 2026.6.1 режима нет или он
   устроен иначе — остановиться и сообщить, предложить альтернативу (ручные «двойные
   флипы» / ступеньки стиков по протоколу).
2. **Мастер chirp-полёта**: какие параметры выставить (CLI-блок, через B5 — применить),
   как назначить тумблер, как лететь (висение, по оси по очереди, сколько секунд), меры
   безопасности (высота, открытое место, готовность выключить).
3. **Анализ chirp-участков**: частотная характеристика замкнутого контура и объекта
   по каждой оси (АЧХ/ФЧХ, когерентность — где данным можно верить), запасы устойчивости
   (по фазе и амплитуде), полоса пропускания. Модель оси (`src/sysid/`) подбирать по
   chirp-данным вместо step response, когда они есть, — сравнить fit и ширину полосы
   прогноза «по фристайлу» и «по chirp».
4. **Советчик**: новые правила на запасах устойчивости («запас по фазе мал → не
   поднимать P/D, сначала задержка фильтров»), с ID, версиями, тестами — по тем же
   правилам, что этап 4 (механика первая, ≤ 2 изменений, шаг ≤ 10–15 %, правило
   безопасности для подъёма D).
5. Прогноз PID по chirp-модели — по-прежнему **прогноз** (пунктир + полоса + «проверь
   полётом»), но полоса должна стать заметно уже; показать, насколько.

Проверка: синтетика — объект с известной АЧХ и задержкой, chirp-вход → утилита
восстанавливает АЧХ (±1 дБ в полосе когерентности) и запасы устойчивости; на реальном
chirp-логе пользователя (когда появится) — модель по chirp предсказывает step response
обычного полёта лучше, чем модель по фристайлу.

## D. Синхронизация с видео из очков DJI

1. **Открыть MOV/MP4** рядом с логом (без загрузки в память: `URL.createObjectURL`).
   Время записи и длительность — из атомов `mvhd`/`tkhd` (порт `bb-tools/movmeta.js` в
   TS, читать только нужные куски файла).
2. **Автосинхронизация**: грубо — по `Log start datetime` и времени создания MOV
   (учесть, что часы очков и полётника разные и могут не совпадать на минуты); точно —
   по событию, видимому в обоих: арм/старт моторов, панч, удар (пик ускорения ↔ резкий
   рывок кадра). Дать ручную подстройку смещения (± кадр) и сохранять её в сессию.
3. **Общий курсор**: видео следует за курсором графиков и наоборот; клик по событию в
   «Полёт и события» перематывает видео. Режим «покадрово» вокруг срыва.
4. Поверх видео — небольшой оверлей (газ, °/с, напряжение) по желанию.
5. Если браузер не умеет кодек (DJI часто пишет H.265) — сказать честно, что делать
   (Edge/Chrome с аппаратным HEVC, или перекодировать), не падать.

Проверка: тест разбора атомов на маленьком синтетическом MOV (сгенерировать в тесте),
тест сдвига времени; ручная проверка на видео пользователя (положить короткий фрагмент
в `tests/fixtures/` только если пользователь согласится — это личные данные).

## E. CI на GitHub и несколько бортов

### E1. CI (GitHub Actions)

1. Workflow на каждый PR и push в `main`: `npm ci` → `npx tsc --noEmit` → `npm test` →
   `npm run build`; собранный `dist/index.html` — артефактом PR (скачать и открыть
   двойным кликом).
2. **Без большого дампа**: `actions/checkout` с `lfs: false`. Тесты большого дампа уже
   умеют пропускаться, когда вместо файла лежит LFS-указатель (`hasFixture`). Каждый
   прогон с LFS тянул бы 133 МБ из бесплатного лимита 1 ГБ/мес. В отчёте CI явно
   писать, сколько тестов пропущено и почему («полный прогон — локально, `git lfs pull`»).
3. Кэш `node_modules` по `package-lock.json`, версия Node — та же, что локально
   (зафиксировать в `.nvmrc` или `engines`).
4. Проверить, что CI реально ловит поломку: временный PR с упавшим тестом → красный
   статус; убрать.
5. Описать в `CLAUDE.md`: что CI не проверяет (большой дамп, `file://`, железо) и что
   это делается локально перед слиянием.

### E2. Несколько бортов

Сейчас борт (проект) определяется по `Craft name`, а при пустом имени — по модели платы.
Два квадрика на одинаковых полётниках сливаются в один, а полётник, переставленный в
новую раму, остаётся «тем же бортом».

1. **Ключ борта**: `DeviceUID` из заголовка (уникальный ID процессора) + `Craft name`;
   при первой встрече — диалог «это новый борт или существующий?». Явная операция
   «полётник переехал в новую раму» — новый борт, история старого сохраняется, связь
   «тот же FC» видна. Миграция существующих сессий без потерь (тест на импорте старого
   JSON).
2. **Класс борта** в профиле (вместо свободного текста — структурированные поля): размер
   пропа (65/85 мм вупы, 3", 5", 7", 10"), число банок, KV, вес, рама. От класса зависят
   пороги: сейчас всё откалибровано на 5" 6S (шум, D-term, разброс моторов, сопротивление
   пакета, «медленный» отклик). Сделать **переопределения порогов по классу** в
   `analysis.json` (`classes: { "7in": { … } }`), с честной пометкой в UI «порог для 7"
   не откалиброван — по аналогии с 5"», пока нет данных; советчик читает класс.
3. **Быстрое переключение**: список бортов в шапке, у каждого — последний полёт, статус
   светофора, открытая кампания (A1).
4. **Сравнение между бортами** (информационное, не для советов): шум до/после фильтров,
   задержка фильтров, step response, моторы — на одном графике, с нормировкой по газу и
   **явным предупреждением**, что борта разные и выводы — только ориентир («у 7" шум ниже
   по частоте — это нормально»).
5. **Перенос настроек**: «взять фильтры/рейты с борта X как старт для Y» — CLI-блок с
   проверкой диапазонов версии прошивки Y и предупреждением, что механика другая.

Проверка: тесты ключа борта (два лога с одинаковой платой и разным `DeviceUID` → два
борта; тот же `DeviceUID` после «переезда» → новый борт со ссылкой), миграция старого
экспорта, переопределение порога по классу меняет светофор и советчик; CI зелёный на PR.

## Порядок работы

0. **E1** (CI) — первым и маленьким PR: дальше каждый PR проверяется автоматически.
1. **B1–B3** (подключение, стирание, скачивание) — сразу снимает главную боль.
2. **E2.1** (ключ борта по `DeviceUID`) — до кампаний, чтобы история бортов не перепуталась.
3. **A1–A2** (кампания и протокол тестового полёта) — с напоминанием про стирание из B2.
4. **B4–B5** (чтение настроек, применение CLI с бэкапом и откатом).
5. **D** (видео) — помогает разбирать срывы.
6. **E2.2–E2.5** (классы бортов, переключение, сравнение, перенос настроек).
7. **C** (chirp) — после сверки по исходникам.
8. **A3–A5** (точность, предложения порогов, экспорт) — когда накопятся кампании.

После каждого шага: тесты, `npx tsc --noEmit`, сборка, проверка `file://`, обновлённые
`PLAN.md` / `CLAUDE.md`, подсказки к новым элементам, PR с описанием «что сделано /
как проверить / что не проверено на железе».

## Чего не делать

- Ничего не писать в полётник без явного нажатия пользователя и не на disarmed-борт;
  никаких команд, способных крутить моторы.
- Не выдавать прогноз за факт; не прятать правки порогов — только через
  `analysis.json` с историей и тестом.
- Не утверждать по памяти коды MSP, имена CLI-параметров chirp и форматы — сверять с
  исходниками нужной версии и ссылаться на них.
- Не класть личные видео и логи в репозиторий без согласия.
- Не тащить сервер, аккаунты, телеметрию; всё локально.
