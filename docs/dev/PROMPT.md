## Задача

Построй **Blackbox Studio** — локальную утилиту, которая:

1. открывает лог Betaflight (`.bbl` / `.bfl` / `.txt` — полный дамп флешки);
2. разбирает его и показывает понятную картину: шумы, фильтры, отработку PID,
   рейты, моторы, питание, события;
3. **предлагает конкретные настройки** (CLI-команды `set ... = ...`
   и/или положения слайдеров Simplified Tuning);
4. **визуализирует результат этих настроек ещё до полёта** — пересчитывая
   записанные данные через новую цепочку фильтров и новые рейты, и прогнозируя
   step response;
5. принимает **повторный лог после перенастройки** и показывает честное
   сравнение «до / прогноз / после».

Цикл работы пользователя: летаю → гружу лог → читаю, что не так →
крутлю предложенные ползунки и сразу вижу эффект на графиках → копирую CLI
в конфигуратор → летаю → гружу второй лог → смотрю, сбылся ли прогноз.

### Известные грабли, которые декодер обязан обрабатывать

- **Начало лога** — маркер `H Product:Blackbox flight data recorder`. В одном
  файле может быть много логов: показать список (дата, длительность, прошивка),
  дать выбрать.
- **Заворот адреса флешки W25N01GV** (Betaflight ≤ 2026.6.1, исправлено в PR
  #15524): данные повторяются с периодом ровно 64 МиБ. Всё, что выше границы, —
  дубль или мусор поверх старого. Детектировать повтор, дубликаты не показывать,
  пользователю сказать человеческим языком, что случилось и что делать (стирать
  флешку перед каждой сессией).
- **Дубль 64-байтного куска внутри строки заголовка** (≤ 2026.6, PR #15525):
  список имён полей склеен из обрывков через `:`. Уже вылечено в `bbdec.js`:
  берём сегмент, у которого число полей совпадает со строками
  signed/predictor/encoding.
- Битые кадры: ресинхронизация по следующему корректному I-кадру, учёт
  процента потерь, отметка «дыр» на временной шкале.
- Частота логирования = `1e6 / looptime / P interval`
  (`pid_process_denom` учитывать). На моём Velox сейчас `looptime:125`,
  `P interval:4` → **2 кГц логирования, Найквист 1 кГц**; старые логи на 4.5.2
  были 1 кГц. Всё, что выше Найквиста, утилита честно не видит — так и писать.
- eRPM → Гц мотора: `eRPM × 100 / (motor_poles / 2) / 60`.
- Если `gyroUnfilt` нет в логе (`debug_mode` не тот или поле отключено в
  `fields_disabled_mask`), анализ фильтров деградирует — показать, какую
  настройку включить для следующего полёта.

## Обязательные требования

### 1. Понятный интерфейс

- Стек: **локальное веб-приложение** — Vite + TypeScript, графики на
  uPlot (миллионы точек без тормозов) или ECharts для тепловых карт. Python
  на машине нет, Node есть. Запуск одной командой (`npm run dev` или собранный
  `index.html`, открывающийся без сервера). Электрон — только если без него
  никак.
- Декодирование и тяжёлая математика — в **Web Worker**, интерфейс не
  замирает; прогресс-бар при загрузке больших дампов. Потоковое чтение файла,
  а не `readFileSync` всего дампа в память.
- Структура экрана:
  1. **Сводка («Светофор»)** — 6–8 карточек: Шумы, Фильтры (задержка),
     Отработка PID, Feedforward, Моторы, Питание, Связь, Целостность лога.
     Каждая — зелёная/жёлтая/красная + одна фраза («Шум на питче выше нормы
     на 180–220 Гц — похоже на резонанс рамы»).
  2. **Шумы** — спектр (до/после фильтров), спектрограмма «частота × газ»
     и «частота × время», линии гармоник моторов из eRPM поверх.
  3. **Фильтры** — АЧХ и ФЧХ всей цепочки, задержка в мс на 100 Гц,
     сравнение «сколько шума срезали / сколько задержки добавили».
  4. **PID / step response** — переходная характеристика по каждой оси,
     overshoot, время нарастания, ошибка трекинга setpoint, P/I/D/F вклад.
  5. **Рейты** — кривая стик → °/с для текущих и предлагаемых рейтов, плюс
     гистограмма: где реально находились стики в полёте.
  6. **Моторы и питание** — насыщение, разброс между моторами, десинки,
     просадки, внутреннее сопротивление пакета.
  7. **Полёт и события** — временная шкала с режимами, арм/дизарм, failsafe,
     найденными аномалиями; клик → зум всех графиков на этот момент.
  8. **Настройка** — панель «песочница» (см. п. 4).
  9. **Сравнение** — до / прогноз / после.
- Тёмная тема по умолчанию, светлая — переключателем. Русский язык
  интерфейса, все строки в одном файле локализации.
- Синхронный курсор и зум по времени на всех графиках вкладки.
- Выбор участка лога мышью (исключить взлёт, краш, стояние на земле);
  по умолчанию анализ берёт только «чистый полёт»: armed, газ выше холостого,
  без краша, без failsafe.

### 2. Подсказки с разжёванным текстом

У **каждого** графика, метрики и параметра — кнопка «?» с объяснением в
три уровня:

- **Коротко** (1 строка): «Это шум, который видит гироскоп до фильтров».
- **Подробно** (абзац, без формул): что это физически, откуда берётся,
  как выглядит норма и как — проблема. С аналогией из жизни, если она
  честная.
- **Для тюнера**: какие параметры на это влияют, в какую сторону крутить,
  чем платим (задержка ↔ шум, резкость ↔ перегрев моторов, overshoot ↔
  propwash).

Плюс:

- Каждая рекомендация отвечает на вопросы: **что увидели** (с цифрой и
  ссылкой на график), **почему это плохо**, **что поменять**, **что
  ожидаем**, **риск** (горячие моторы, осцилляции, вибрации в видео) и
  **как проверить** после полёта.
- Глоссарий терминов (PT1, нотч, Q, D-term, feedforward, propwash, TPA,
  Найквист…) с перекрёстными ссылками из подсказок.
- Тексты подсказок — в отдельных Markdown/JSON-файлах, чтобы я мог
  дописывать сам без правки кода.
- Никаких «попробуй и посмотри» без объяснения, на что смотреть.
- **Правило безопасности**: каждая подсказка, поднимающая D или
  ослабляющая фильтры, предупреждает: после изменения — короткий висящий
  полёт 20–30 с и **потрогать моторы**. Если горячие — откат.

### 3. Повторный анализ: до / после

- Проект = борт. Внутри — **сессии** (лог + снимок настроек из его заголовка
  + мои заметки + предложенные изменения). Хранить в IndexedDB и уметь
  экспорт/импорт в один JSON-файл.
- Сравнение любых двух сессий: наложенные спектры, step response,
  метрики в таблице с дельтой и стрелкой «лучше/хуже».
- **Diff настроек** между сессиями берётся автоматически из заголовков
  логов (все `H ...` параметры), с подсветкой изменённых.
- **Честность сравнения**: полёты разные. Сравнивать только сопоставимые
  режимы — нормировать по газу (бины газа), по интенсивности стиков,
  по напряжению. Если в одном логе только висение, а в другом фристайл —
  явно предупреждать, что сравнение некорректно, и показать, в каких
  бинах данных хватает.
- Три линии на каждом сравнительном графике: **«было»**, **«прогноз»**
  (что утилита обещала для новых настроек) и **«стало»** (реальный второй
  лог). Отдельная метрика «точность прогноза» — так я пойму, насколько
  ей доверять.

### 4. Рекомендации и визуализация результата новых настроек

Это главная фича. Пользователь двигает ползунки (или жмёт «Применить
рекомендации») — и **сразу**, без полёта, видит, как изменятся графики.
Важно разделить, что можно посчитать точно, а что — только спрогнозировать,
и **показывать это в интерфейсе разными стилями** (сплошная линия —
точный пересчёт, пунктир с полосой неопределённости — модель).

**а) Фильтры — точный пересчёт.**
Цепочка фильтров Betaflight детерминирована. Взять записанный
`gyroUnfilt`, прогнать через **реализацию фильтров один в один как в
прошивке** (PT1/PT2/PT3/biquad с теми же формулами коэффициентов на
частоте PID-цикла; dynamic LPF от газа; RPM-нотчи с центрами из
записанного eRPM, гармоники 1..N, fade range; динамический нотч —
воспроизвести алгоритм SDFT/поиска пиков максимально близко к исходнику
`src/main/flight/` и `src/main/sensors/gyro_filter`/`dyn_notch_filter`).
Результат:
- новый спектр «после фильтров» поверх старого — видно, что шум срезан;
- новая задержка фильтров (групповая задержка на 50/100/150 Гц в мс);
- точность проверить: прогнать **текущие** настройки через симулятор
  и сравнить с записанным `gyroADC` — расхождение должно быть малым,
  показать его числом в UI («модель фильтров совпадает с бортом на 97%»).
  Если сильно расходится — не давать советов по фильтрам, честно сказать.

**Оговорка про частоты**: при логировании 2 кГц пересчёт видит только до
1 кГц, а фильтры работают на 8 кГц. Для фильтров это допустимо (шум выше
1 кГц в лог всё равно не попал — объяснить это в подсказке), но учитывать
алиасинг.

**б) D-term — точный пересчёт.** То же для D-term: D из нового
отфильтрованного гиро с новыми `dterm_lpf*` → спектр D-term и его RMS
(прокси нагрева моторов).

**в) Рейты — точный пересчёт.** Записанные `rcCommand` прогнать через
новую формулу рейтов (все `rates_type`, формулы из `rc.c`) → новый
setpoint по времени + кривая стик→°/с + max rate. Показать «на этом
флипе ты бы крутился 1100 °/с вместо 850».

**г) PID — прогноз по модели.**
- Идентифицировать модель «команда PID на ось → угловая скорость»
  по каждой оси из лога (например ARX/второй порядок + задержка, на
  участках с хорошим возбуждением стиками). Показать качество модели
  (fit %); если данных мало — не прогнозировать.
- Замкнуть модель с новыми P/I/D/FF/D_max и новыми фильтрами →
  прогноз step response и трекинга setpoint на **записанных стиках**.
- Измеренный step response — через deconvolution setpoint→gyro
  (метод PIDtoolbox/PID-Analyzer), усреднение по окнам, отбрасывание
  окон с насыщением моторов.
- Прогноз всегда с полосой неопределённости и подписью «модель,
  проверь полётом».

**д) Движок рекомендаций.**
- Правила на прозрачных порогах, вынесенных в конфиг (а не магия в коде).
  Каждое правило: условие → изменение → объяснение → ожидаемый эффект →
  риск. Примеры:
  - низкий шум по всему спектру и чистый D-term → можно поднять
    `simplified_gyro_filter_multiplier` / `dterm_filter_multiplier`
    (меньше задержки);
  - узкий пик, не привязанный к гармоникам моторов и не зависящий от
    газа → резонанс рамы → проверить, попадает ли в диапазон
    `dyn_notch_min/max_hz`, при необходимости сузить диапазон;
  - пики на гармониках eRPM, плохо подавленные → `rpm_filter_q`,
    число гармоник; RPM-фильтр уже стоит — сначала искать механику
    (пропы, подшипники, люфт мотора);
  - overshoot > 15% на шаге → меньше P / больше D;
  - медленное нарастание, «ватный» отклик → больше P/FF;
  - высокий RMS D-term → риск перегрева, D не поднимать, сначала
    фильтры/механика;
  - насыщение моторов на манёврах → проблема авторитета, не PID
    (пропы, вес, airmode, газовая кривая);
  - пульсации vbat и высокое сопротивление → пакет/проводка/конденсатор,
    а не тюнинг.
- Отдельно различать «чинится настройкой» и «чинится руками» (механика,
  пропы, демпферы, проводка). Механику не маскировать фильтрами.
- Шаг изменений ограничен: не больше одного–двух параметров за итерацию
  и не больше ±10–15% за раз. Для очень грязного борта — сначала
  механика, потом настройки.
- Выдача: готовый блок CLI (`set ...` + `save`) с кнопкой «Копировать»,
  и вариант для Simplified Tuning (какой слайдер куда). Предупреждение,
  если `simplified_*` перезапишут ручные значения.
- Никогда не выдавать настройки, выходящие за допустимые диапазоны
  параметров Betaflight своей версии.

### 5. Обучение на ошибках (журнал инцидентов)

Утилита будет ошибаться — модели неточные, правила грубые. Нужен
**встроенный цикл исправления**: я летаю по её совету → если что-то пошло
не так, фиксирую это в утилите → потом прошу Claude (тебя) в новой сессии
разобрать случай и поправить утилиту → исправленная версия эту ошибку
больше не повторяет. Никакого «самообучения» нейросетью: обучение =
явные, проверяемые правки правил и порогов + автоматическая калибровка
прогнозов по истории.

**а) Каждая рекомендация отслеживается.**
- У каждого правила советчика стабильный ID (`R-FILTER-RAISE-GYRO-01`)
  и версия. В сессии хранится: какие правила сработали, на каких цифрах,
  что предложено, что я **реально применил** (сверка по заголовку
  следующего лога, а не по моим словам), какой был прогноз.
- Если я применил не всё или поменял что-то сам — это видно в diff, и
  результат не приписывается правилу, которое я не применял.

**б) Отметка «пошло не так» после полёта.**
Кнопка «Сообщить о проблеме» на сессии «после». Форма:
- симптом из списка + своими словами: горячие моторы, осцилляции/дрожь
  на висении, «качели» при сбросе газа (propwash), bounce-back после
  флипа, вялость, дрейф, вибрация в видео, десинк, краш, другое;
- когда (время в логе — можно ткнуть в график), насколько сильно (1–3),
  температура моторов на ощупь;
- приложить видео/заметку (опционально).
Утилита сама дополняет случай: метрики до/после, что прогнозировалось и
что вышло, какие правила сработали, где прогноз разошёлся сильнее всего,
и **автоматически ищет признаки** (рост D-term RMS, новые пики в спектре,
рост overshoot, насыщение моторов) — подсвечивает подозреваемое правило.

**в) Папка случая для разбора Claude.**
Каждый инцидент экспортируется в файлы на диске, которые я смогу
показать тебе в следующей сессии:

```
blackbox-studio/cases/INC-0007-hot-motors/
  case.md          # человеческое описание: симптом, что советовали, что вышло
  case.json        # всё машинно: сессии, diff настроек, сработавшие правила
                   # (ID+версия+входные цифры), прогноз vs факт, метрики
  before.bbl / after.bbl   # или ссылки + смещения логов в дампе
  plots/*.png      # ключевые графики до/прогноз/после
  resolution.md    # заполняется при исправлении: причина, что поменяли, коммит
```

Плюс файл `blackbox-studio/CLAUDE.md` — **инструкция для тебя** на
будущие сессии: как разбирать случай (воспроизвести анализ на логах,
найти, какое правило/порог/модель ошиблись, отличить ошибку утилиты от
механики/внешних условий), как вносить правку, что обязательно обновить
и прогнать. Пиши его сразу и поддерживай актуальным.

**г) Правка = регрессионный тест.**
- Каждый разобранный инцидент превращается в тест в `tests/cases/`:
  «на этих логах советчик НЕ должен предлагать X» / «должен
  предупредить о Y» / «прогноз overshoot должен быть в пределах Z».
- Перед любой правкой правил прогоняются все прошлые случаи: правка,
  которая чинит INC-0007, но заново ломает INC-0003, не принимается.
- Пороги и правила лежат в версионируемом конфиге (`advisor/rules.json`
  или `.ts` с декларативным описанием), у каждого — история изменений
  со ссылкой на инцидент (`changed in v1.4 by INC-0007: ...`).
- Варианты исправления, от предпочтительного к крайнему:
  уточнить условие правила → сдвинуть порог → уменьшить шаг изменения →
  добавить предупреждение/обязательную проверку → отключить правило для
  этого класса бортов.

**д) Автоматическая калибровка без меня.**
- По всем парам «прогноз → факт» утилита считает ошибку прогноза по
  каждой метрике и **расширяет/сужает полосу неопределённости** и
  «уровень доверия» правила для конкретного борта.
- Правило, которое на этом борту 2 раза из 3 давало результат хуже —
  автоматически понижается до «совет с осторожностью» с объяснением
  почему («на этом квадре подъём D дважды грел моторы: INC-0004, INC-0007»).
- Профиль борта копит знание: размер пропов, моторы KV, вес, тип рамы,
  известные резонансы, «чувствительность к D», температура моторов из
  моих отметок. Правила читают этот профиль.

**е) Откат.**
К каждой сессии — кнопка «Вернуть прошлые настройки»: CLI-блок,
возвращающий значения из предыдущего удачного лога. Для инцидента
уровня «краш / сильные осцилляции» — откат показывается первым,
крупно, до любых объяснений.

## Чего не делать

- Не изобретать «умный» ИИ-советчик без объяснимых правил: каждая
  рекомендация должна прослеживаться до цифры на графике.
- Не выдавать прогноз за факт. Пересчёт фильтров и рейтов — факт,
  прогноз PID — модель.
- Не советовать ослабить фильтры на грязном борту «ради отклика».
- Не прятать «обучение» в непрозрачные веса: каждая правка поведения
  советчика — это видимое изменение правила/порога со ссылкой на
  инцидент и тест.
- Не тащить Python, сервер в облаке, аккаунты и телеметрию.
- Не ломать мои существующие скрипты в `bb-tools` — новая утилита
  живёт в отдельной папке `Desktop\claud\blackbox-studio`.
